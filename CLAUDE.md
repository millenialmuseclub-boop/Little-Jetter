## Working architecture

- Main UI: `src/LittleJetterApp.tsx` — one large component file. Yes, it's big; that's the existing convention, not a mistake to "fix" by splitting it up unasked.
- Styles: `src/little-jetter.css` — one large plain-CSS file, same convention.
- Wardrobe catalog: `src/data/dressUpCatalog.json` — destination → slot → item. **Nearly everything now lives under `destinations.all`** (see Wardrobe below), not per-destination.
- Explore-tab content: `src/data/exploreContent.json` — gastronomy/vocabulary/sites/mad-lib per destination, keyed by destination id. All 38 destinations are covered.
- Client-side pending/preload helper: `src/data/garmentManifest.ts`
- Illustrated assets: `public/little-jetter/catalog/tokyo/<item-id>/default.png` — despite the `tokyo` folder name, these are used by every destination now (see Wardrobe below). The folder name is legacy/historical, not a scoping signal.
- Destination backdrop photos: `public/little-jetter/<destination-id>-doll-backdrop.png` — every one of the 38 destinations has a real painterly photo now (see `DESTINATIONS_WITH_BACKDROP` in `LittleJetterApp.tsx`, which currently == all 38; keep it in sync if a destination is ever added without a backdrop).
- LTK product references (Shop tab): `src/data/realProducts.ts`, generated by `scripts/build-real-products.mjs` from `scripts/ltk-import.csv` + `scripts/product-image-overrides.json` (id → real photo URL, merged in so re-running the CSV import never wipes resolved photos). `src/catalog.ts` just re-exports it.
- Asset specification (original hand-painted pipeline, mostly historical now): `docs/wardrobe-asset-template.md`
- Asset generation pipeline (model-generated art, still works but unused this pass): `server/closet/`, `api/admin/closet/`, `docs/closet-asset-generation.md`

`server/`, `api/`, and `scripts/*.ts` are server-only Node code, deliberately kept outside `src/`'s TypeScript project so they can use `fs`/`process`/`Buffer` without breaking the browser build (checked separately with `npm run typecheck:server`). Never import anything from `server/` into `src/LittleJetterApp.tsx` or its dependency graph. Scripts under `scripts/*.mjs` are exempt from that typecheck (plain Node, no TS project).

## Wardrobe: how it actually works now (read this before touching clothing)

This changed substantially this pass — old assumptions from an earlier version of this doc no longer apply:

- The **Style tab drawer list** for every slot is driven by `wardrobe[group]` where `const wardrobe = catalog.destinations.all` — i.e. it reads from the `all` bucket, filtered by tag (`item.tags.includes('destination:all') || item.tags.includes('destination:' + selectedId)`). **New wardrobe items belong in `destinations.all`, tagged `'destination:all'`, not in a per-destination bucket** — the product intentionally has one universal closet, not per-city wardrobes.
- 5 real equip slots exist in `Picks`/`CatalogDestination`: `tops`, `bottoms`, `layers` (outerwear), `shoes`, `accessories`. There is deliberately **no separate `dresses`/`hats`/`pajamas`/`swim` slot** in the type system — those are UI-only filtered *views* into `tops` or `accessories`, controlled by `styleFilter` state (`'dress' | 'pajama' | 'swim' | 'hat' | null`) and an extra tag on the item (`style:dress`, `style:pajama`, `style:swim`, `style:hat`). See `availableWardrobe()` in `LittleJetterApp.tsx` for the exact filter logic, and the 4 extra rail buttons (Dress/Pajamas/Swim/Hat) next to the 5 real `CLOSET_GROUPS` buttons.
- **Hats are the one exception that got a real independent equip state**: `hatPick` (separate `useState`, not part of `picks`), so a kid can wear a hat *and* a bag/other accessory at once instead of the hat competing with everything else for the single `accessories` slot. It renders as its own `layer-hat` image layer in `CatalogDoll`, looked up from the same `accessories` catalog array via `hatPick` instead of `picks.accessories`. If you add more hat items, just tag them `style:hat` in the `accessories` bucket — no other wiring needed.
- **129 clip-art clothing items** were extracted this pass from a hand-drawn reference sheet (`scripts/clipart-catalog.mjs` has the full manual id→category→anchor mapping; `scripts/position-clipart.mjs` does the actual placement using calibrated per-anchor target widths — **not** the full slot-safe bound, see the big comment at the top of that file for why; `scripts/wire-clipart-catalog.mjs` writes them into `dressUpCatalog.json`). These are flat/laid-out illustrations, not worn-pose art like the original hand-painted set — placement is a best-effort center-and-scale, not anchor-matched joints. If more clip-art sheets come in, follow the same 3-script pipeline; the connected-component blob-extraction approach (see git history around commit `aac2ceb`) is the fastest way to pull individual items off a packed reference sheet.
- **Sunglasses were deliberately removed** (all 6 variants) per direct request — don't re-add them if you see them in old git history or a stray reference sheet.
- One orphaned mini-batch never got wired in: `public/little-jetter/catalog/tokyo/tokyo-bucket-hat/` and `tokyo-tote-bag/` (untracked in git, `scripts/generate-batch-4.ts` produced them). **Don't wire these in as-is** — the tote bag has a real motif QC bug (it's drawn with an Eiffel Tower silhouette on a "TOKYO" tote, which breaks the never-borrow-another-destination's-icon rule documented below). Fix the art or regenerate before adding to the catalog, or just delete the orphan folders if not worth pursuing.
- Garments can be **dragged, pinch-resized, and rotated directly on the doll** (`garmentScale`/`garmentOffset`/`garmentZBoost`/`garmentRotation` state in `LittleJetterApp.tsx`, generic hit-testing via `hitTestDoll()` on any `img[data-item-id]` layer). This applies to the head and the base body layer too (`data-item-id="head"` / `"body"`), not just equipped clothing.
- Motif rule still applies: every asset must belong to its own destination's visual language — never another destination's landmark/icon. This is why the orphaned tote bag above is blocked.

## Destinations

All **38 destinations** are live, each with: full data entry in the `destinations` array (`LittleJetterApp.tsx`) — region, weather, adventure text, 4 journal notices, passport phrase, etc. — a real painterly backdrop photo, and full Explore-tab content (`exploreContent.json`: gastronomy, vocabulary, sites-to-see, mad-lib). The destination-selector cards show each destination's own real backdrop photo (not a shared generic placeholder — that was a bug, fixed).

If you add a 39th destination: it needs all four of (1) a `destinations` array entry, (2) a `-doll-backdrop.png` file + entry in `DESTINATIONS_WITH_BACKDROP`, (3) an `exploreContent.json` entry, (4) nothing wardrobe-related — the wardrobe is universal per above.

## Explore tab

Redesigned into 5 sub-pages this pass, driven by `exploreView` state: **Kindness journal** (gratitude/kindness prompts, persisted to `localStorage` under `little-jetter-kindness-journal`), **Gastronomy**, **Silly memory** (the mad-lib), **Words** (vocabulary), **Sites to see**. Content for all of these comes from `exploreContent.json` per destination — don't hardcode destination-specific content in the component.

## The adventure ticker

The "your next adventure" UI went through several redesigns this pass and landed on: a **thin (30px) dark strip with monospace amber scrolling marquee text**, styled like an airport/ferry split-flap departure board — not a card, not a big button. It's rendered **inline in the destination grid, right after whichever destination card is currently selected** (`isSelected` check in the `.little-country-cities` map), not fixed to the screen edge — it should visually "pop up" at the point of interaction. It includes 3 small quick-jump stops (GO/CONTINUE, EXPL, SHOP) mirroring the main step nav. CSS class names: `little-adventure-ticker*` — note these were deliberately renamed away from `little-ticker*` because that prefix was already used by an unrelated destination-type filter UI (`.little-ticker-track`/`.little-ticker-row` in the `little-type-filter` component); a first draft of this feature silently broke that other UI by reusing the same class names. Watch for this if touching either.

## Required acceptance test for any dress-up/doll change

Do not report a dress-up change complete from state, captions, or console checks alone.

1. Open Style and scroll to the doll and closet.
2. Capture the doll stage.
3. Select items across each drawer, including the Dress/Pajamas/Swim/Hat filtered views and a hat + a separate accessory together.
4. Capture the same doll-stage region after every selection.
5. Confirm pixels visibly change in the selected slot — not merely the caption.
6. Confirm the drawer thumbnail matches the equipped artwork.
7. Confirm variant swatches (where present) change to distinct image files.
8. Repeat at a 390px mobile viewport.
9. Run `npm run build` and `npm run lint` before committing. If `server/`, `api/`, or `scripts/*.ts` changed, also run `npm run typecheck:server` (plain `.mjs` scripts are exempt).

## Commands

- `npm run dev` — local dev server (Vite)
- `npm run build` — `tsc -b && vite build`, must pass clean before every commit
- `npm run lint` — `oxlint`, must pass clean before every commit
- `npm run typecheck:server` — only needed if `server/`, `api/`, or `scripts/*.ts` changed
- `npx vercel deploy --prod` (from inside `little-jetter/`) — the only reliable way to update production right now, see Known open items above
